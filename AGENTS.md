# MixLab — Agent Instructions

Weight-first e-liquid calculator with inventory, cost tracking, and a guided
weigh-along mode. Flutter, cross-platform (macOS/Windows/Linux/iOS/Android/web).
Fully offline — no network calls, no telemetry, no accounts. All state is local
via `shared_preferences`.

## Commands

```bash
flutter pub get                   # install deps
flutter test                      # run tests
flutter test test/foo_test.dart   # single file
flutter analyze                   # static analysis — must be clean
dart format .                     # format
flutter run -d macos              # run (or windows, linux, chrome, <device-id>)
```

Before any commit: `flutter analyze` clean, `flutter test` green, `dart format .`
applied. Do not commit with analyzer warnings.

## Domain Rules

These are correctness constraints, not style preferences. Violating them
produces wrong numbers in a tool people use to mix inhalable nicotine.

**Weight is the source of truth.** The app computes grams, not millilitres.
Do not "simplify" a weight calculation by routing it through a volume
intermediate.

**Density is per-ingredient and carrier-aware.** Density is derived from the
ingredient's kind and its carrier VG percentage. Never introduce a shared
density constant. A 100 mg/mL nicotine base in VG is ~1.26 g/mL; assuming a
PG-based ~1.036 is a ~20% error on the most safety-critical ingredient.

**Achieved values are recalculated from real weights.** When a user overpours,
downstream nicotine strength and PG/VG ratio must be recomputed from what was
actually weighed — not from the plan. Any change that makes a displayed value
revert to the planned figure is a bug.

**Floating point.** Weights and percentages are floats. Do not compare with `==`.
Do not add rounding at intermediate steps — round only at display. If you change
where rounding happens, add a test proving totals still reconcile.

**Persistence is versioned.** The schema has a version number and forward
migrations. If you change a persisted model:
1. Bump the schema version
2. Write a forward migration
3. Add a test loading old-format data

Loading data from a newer build must refuse, not corrupt. Never write a
migration that discards unknown fields.

**Export/import merges by id.** Importing the same file twice must be a no-op,
not a duplication. Preserve this invariant.

**Undo is exact.** Mix logging deducts from inventory; undo restores the precise
amounts deducted. Restock undo restores the previous stock *and* cost basis.
Approximate or recomputed restores are wrong.

**Offline is a hard guarantee.** Never add a dependency or code path that makes
a network request, phones home, or requires an account. This is a core promise
in the README.

## Conventions

- Follow `analysis_options.yaml`. If a lint fires, fix the code, don't add
  an ignore comment.
- Prefer adding a test over adding a comment explaining why something is tricky.
- Calculation logic belongs in pure, testable functions separate from widgets.
  If you touch calculation code that currently lives in a widget, extracting it
  is welcome — but as its own change, not smuggled into a bug fix.

## Improvement Scope

**Allowed without asking:**
- Fixing failing tests
- Adding tests for untested calculation, migration, or inventory logic
- Fixing genuine bugs with a reproducing test
- Removing provably dead code (verify nothing references it first)
- Fixing analyzer warnings

**Ask first:**
- Any change to density formulas, nicotine math, or PG/VG ratio logic
- Any change to the persistence schema or migrations
- Adding, removing, or upgrading dependencies in `pubspec.yaml`
- Renaming public APIs or changing function signatures
- Restructuring directories
- Editing platform directories
- Anything touching the weigh-along step sequence

**Never:**
- Add features not requested
- Add network calls, analytics, or crash reporting
- Change the README's capability comparison tables — those are claims about
  behavior and only change when behavior does

## Testing

Calculation, migration, and inventory-arithmetic changes require tests. UI-only
changes may not. When fixing a bug, write the failing test first, then fix.

The high-value untested surface is likely: density derivation across carriers,
achieved-value recalculation after overpour, schema migration paths, and
import-merge idempotency. Prefer tests there over widget tests.
